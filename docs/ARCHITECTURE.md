# Архитектура решения Jana Address

Одна строка адреса, как её написал клиент («Нурсити 2 микрорайон 11дом 5 подьезд 239 кв», «Fkvfns? ek/ F,fz 10»,
«Almaty qalasy, Abai daŋğyly 10, 25 päter») → 12 полей в точной схеме жюри + уверенность. Полностью автономно: образ
Docker без сети, старт 1,1 с, 1 000 адресов за 0,7–0,9 с, 84 МБ памяти.

## 1. Конвейер: что происходит с одной строкой

```
raw ──► clean ──► layout_fix ──► tokenize ──► ГРАММАТИКА ──┐
        (невидимые      (не та           (слова, числа,     │ спаны правил + роли токенов
         символы,        раскладка:       пунктуация,        ▼
          )         Fkvfns→Алматы)   «12а», «55/6»)   АРБИТР ◄── ТАГГЕР (ONNX char-CNN+BiLSTM+CRF)
                                                             │  поле за полем: согласие / правило / модель по порогам,
                                                             │  абсолютные правила, вето на «проглоченные» ключевые слова
                                                             ▼
                                                   CANON (conventions.yaml: 16 решений-переключателей)
                                                             │  копируем из строки как написано; нормализуем только
                                                             │  область (таблица) и тип улицы (лемма); «12 корпус 2» → 12/2
                                                             ▼
                                                   ENRICH (справочник OSM: только пустые поля, с происхождением)
                                                             │  область ← город, район ← улица/дом, город ← район
                                                             ▼
                                                   CONFIDENCE (логрегрессия + isotonic, ECE 0,006)
                                                             ▼
                                        ответ жюри ──► АРХИВ (SQLite в томе /data) + геокод (точка, precision, in_database)
```

* **Грамматика** (`api/jana_address/rules/grammar.py`, ~1 400 строк, `lexicon.yaml` ≈ 600 вариантов ключевых слов
  RU / KK / Latin с опечатками и падежами): 14 проходов — телефоны и коды домофона, разделители «/», «—», скобки
  «(бывш. Ленина)», область, связки число↔слово («кв 70», «70 кв», «4подьезд», «д11кв47»), улица с типом до/после имени,
  микрорайон vs дом («Мкр Аксай 3а, 59» ↔ «мкр Жетысу 20»), район, город (ключевое слово, казахский суффикс «қаласы»,
  справочник, нечёткое совпадение «Карагнда»), ЖК / садовые товарищества, ориентиры, исправления внутри строки
  («нет, 12»), остатки. Каждое решение — спан с именем правила и оценкой.
* **Таггер** (`ml/charcrf.py`, `training/train_charcrf.py`): char-CNN (32→96) + эмбеддинг слова (28 678 слов) + форма
  токена + 44 бинарных признака (роли из лексикона, вхождение в множества справочника, контекст) → 2 слоя BiLSTM(128) →
  CRF над 23 BIO-метками. **2,62 млн параметров, ONNX 10,5 МБ, 0,6–0,9 мс на адрес на одном ядре CPU.** Обучен с нуля,
  без предобученных моделей и без интернета в рантайме.
* **Арбитр** (`assembly/arbiter.py`): для каждого поля — согласие (та же позиция), только правило, только модель
  (порог τ_solo), конфликт (модель побеждает выше τ_field; против правила с явным ключевым словом — только выше
  τ_override). Абсолютные правила, которые модель не перебивает: микрорайон, подтверждённый справочником («Аксай 4 мкр»),
  исправление («нет, 12»), пара домов «7-7а», «ЖК X» против спана модели в другом месте. Вето: спан модели, начинающийся
  или кончающийся ключевым словом, которого модель не видела в обучении, проигрывает грамматике; спан имени никогда не
  «съедает» известный город на краю («ЖК Хайвил Астана» → ЖК «Хайвил», город «Астана»). Пороги подобраны перебором
  по метрике жюри (`training/tune_arbiter.py`).
* **Справочник** (`gazetteer/osm.py`, `data_pipeline/build_gazetteer.py`): OpenStreetMap Казахстан → SQLite 36 МБ:
  5 416 населённых пунктов ru/kk/en, 20 областей, районы городов, 5 350 микрорайонов и ЖК, 50 504 улицы, **977 тыс.
  домов с координатами**. Используется трояко: признаки для модели, заполнение пустых справочных полей (никогда не
  переписывает написанное; у каждого значения — происхождение `string` / `string+table` / `gazetteer:osm`),
  геокодирование до дома (96 % реальных адресов) и подсказки при вводе.
* **Уверенность** (`confidence/`): логистическая регрессия на 60 признаках разбора (флаги арбитра, вероятности модели,
  наличие полей) + isotonic; хранится как JSON, в рантайме только numpy. ECE 0,006 на нетронутом наборе: если модель
  говорит 0,9 — она права в ~90 % случаев, значит ей можно отсекать очередь на ручную проверку.
* **Архив** (`archive.py`): каждый прогон — в SQLite в томе `/data`: вход, выход, уверенность, время, точка и
  `precision` (house / street / microdistrict / district / locality / none) → флаг «адрес есть в нашей базе».
  `GET /api/v1/runs`, `/runs/stats`, `/runs/{id}/download`, `/runs/{id}/points` (точки для карты).

## 2. Данные и обучение

| что | сколько | откуда |
|---|---|---|
| Синтетические адреса для обучения | 220 тыс. (v3) + 90 тыс. (v4b) + 120 тыс. с латиницей (v6) + 60 тыс. в каждом дообучении | генератор `training/synth_grammar.py` из OSM: слитные числа, казахский порядок слов, латиница, опечатки, ориентиры, невидимые символы — разметка «по построению» |
| Строки-учителя | **5 861** | Claude Opus 5.5 пишет и размечает адреса по нашим соглашениям (`eval/llm_generate.py`); валидаторы «копируй, не переписывай» отбраковывают ошибки разметки |
| Независимые бенчмарки | 6 наборов, **1 719 адресов** | тот же генератор; каждый «нетронутый» набор замерен один раз до правок — честная оценка |
| Ручная разметка | 416 | отложенный тест, стресс-набор, сёла, 42 примера соглашений |
| Синтетический dev | 5 000 | другой seed генератора |
| Робастность | 21 искажение × 416 адресов, фаззинг 2 500 строк | `eval/robustness.py`, `api/tests/test_fuzz.py` |

Обучение — **только CPU ноутбука (Apple M4)**, GPU университета не понадобился: v3 с нуля 41 мин, затем тёплые старты
(v4b 3 мин, v6 9 мин, v8 7 мин). Выбор версии — по A/B на всех наборах (`make ab`), каждый запуск с хэшем артефактов
записан в `eval/history.jsonl` → `docs/EXPERIMENTS.md`.

История версий модели: v3 (синтетика) → v4b (стресс-набор, более жёсткая синтетика) → v6 (латиница так, как её пишут
клиенты — нашёл независимый бенчмарк) → v7 (789 строк Claude: переобучение, отклонена) → **v8 (5 861 строка Claude ×3 +
бенчмарки + 60 тыс. синтетики)**. Эффект v8 виден ровно там, где должен: на нетронутых наборах (злой 96,47 → 98,98,
региональный 98,49 → 98,94).

## 3. Где здесь Anthropic / Claude

Claude Opus 5.5 (Anthropic API, structured outputs, кэширование промпта) используется **только при подготовке**, никогда
в рантайме:
1. **Независимые бенчмарки** — писатель адресов, который не является автором грамматики (22 региональные + 16 «злых»
   тем). Нашёл: латиницу и транслит, казахские падежные суффиксы, садовые товарищества, исправления в строке, баг в нашем
   собственном промпте разметки (корпус).
2. **Учитель** — 5 861 размеченная строка для v8.
3. **Второе мнение** — `make verify`: наш ответ против ответа Claude, расхождения в страницу ручной проверки
   (`runs/verify/review.html`) и в очередь конфликтов UI.
4. **День 0** — `make day0-claude`: второй независимый разметчик для `train.json` (только с разрешения организаторов;
   без него — `make day0` полностью офлайн: правила ⊕ модель, согласие = эталон, спор = проверка).

Все данные Claude сгенерированы, данные Jana Post наружу не уходят.

## 5. Почему нет внешней базы (Supabase) и зачем архив

Финальный прогон жюри — без сети: любой внешний сервис (Supabase, Postgres в облаке, API карт) в этот момент
недоступен, а решение обязано работать автономно. Поэтому всё состояние живёт внутри контейнера и его тома `/data`:
исправления операторов (`corrections.jsonl`), очередь конфликтов и **архив всех прогонов** (`archive.sqlite`). Это та же
«большая база всего, что мы прогнали», только переносимая вместе с образом: `docker cp` или монтирование тома — и история
у вас. Для онлайн-демо (Render + Vercel) при желании тот же `archive.py` можно направить в Supabase одним адаптером, но
на оценку это не влияет.

## 6. Карта и «есть ли адрес в базе»

Каждая запись после разбора геокодируется по 977 тыс. домов: `precision` = `house` (точный дом) → `house_near` (дом без
корпуса) → `street` → `microdistrict` → `district` → `locality` → `none`; `in_database = precision ∈ {house, house_near}`.
Это и есть индикатор «адрес существует в нашей базе / его нет». Точки для карты отдаёт `GET /api/v1/runs/{id}/points`
и `POST /api/v1/geocode`; схема ответа жюри при этом не меняется (флаг — в explain-режиме и в архиве). Для карты в UI
без интернета достаточно упрощённых контуров областей Казахстана (GeoJSON в образе) и точек по координатам —
тайлы не нужны.

## 7. Правила жюри — где мы

| правило | у нас |
|---|---|
| Docker, автономно, все справочники и модели внутри образа | да: правила + ONNX 10,5 МБ + gazetteer.sqlite 36 МБ; проверка `make offline-check` с `--network none` |
| старт контейнера ≤ 3 мин | 1,1 с |
| 1 000 записей ≤ 5 мин | 0,7–0,9 с |
| словари и справочники приветствуются | лексикон, таблица областей, OSM-справочник, таблица соответствий соглашений |
| запрещено: ответ по id или по точному совпадению всей строки | нет ни одной таблицы «строка → ответ»; ответ строится из токенов; 16 из 21 искажений строки не меняют ответ |
| данные не выносятся | `train.json` в `.gitignore`; Claude — только с разрешения; по умолчанию день 0 полностью офлайн |
